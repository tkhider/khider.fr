Postmortems

externalTrafficPolicy: Cluster corrupted source IPs

2026-09-09 Resolved SEV2 kubernetes traefik networking

I moved Nextcloud off a plain Docker instance and onto the Kubernetes cluster. That same night, its pod failed its readiness probe and dropped out of the Service for about twenty minutes, and Nextcloud started warning that a single address, 10.244.0.0, was being brute-force throttled. Both came from two defaults, one in Traefik and one in Kubernetes, that had been erasing every source IP since Traefik was first set up, two months before Nextcloud was deployed here. No data loss.

Impact

  • Down: the Nextcloud pod was not ready for about twenty minutes on migration night. Single replica, so the app was unreachable through Traefik for that whole window.
  • Degraded: brute-force protection bucketed every client, legitimate or not, under one shared identity, so unrelated traffic could throttle any single user.

Timeline

  • 21:31: Nextcloud's manifests land in the GitOps repo, the migration off the old Docker instance begins.
  • ~22:21, about an hour in: the pod goes not ready and stays that way. KubePodNotReady fires at 22:38, once it crosses the standard 15-minute threshold. It comes back around 22:42, after roughly twenty minutes down.
  • Later that same night: the Nextcloud admin overview starts showing the brute-force banner naming 10.244.0.0. That's what started this investigation.

Trigger

Moving Nextcloud onto the cluster. It was the first app behind Traefik that makes decisions based on the client's IP, through its brute-force protection.

Root cause

10.244.0.0 is the network address of the pod subnet Kubernetes hands out on whichever node the Nextcloud pod lands on. It showed up because two defaults combined to erase the real client IP before it reached the app.

  1. Traefik never forwarded a client-IP header to backends at all. Without forwardedHeaders configured, Traefik does not populate X-Forwarded-For or X-Real-Ip for anything behind it. Nextcloud had nothing to read the real address from, so it fell back to whatever raw address happened to be connecting to it, which is how a pod-network address ended up in the log in the first place.
  2. Traefik itself never saw the real client either. Its own Service, the LoadBalancer that exposes it to the outside, had the default externalTrafficPolicy: Cluster. That setting lets any node handle incoming traffic and rewrites the source address along the way to keep the return path working, so even after forwarding was turned on, Traefik still had the wrong address to forward.

Both of those had been true since Traefik was first deployed, two months before Nextcloud existed on this cluster.

Contributing factors

  • Throttling hit every request. Nextcloud slows down responses when it thinks it's under a brute-force attack. Every request looked like the same attacker, so the slowdown hit almost everything.
  • Few Apache workers, one replica. With most workers stuck on slow responses, there weren't enough left to answer the readiness probe in time. Kubelet marked the pod not ready, and with a single replica the app was unreachable.
  • Nothing else needed the client IP. No other app behind Traefik acts on the source address, so the gap went unnoticed for two months.

Isolation

Every real request, browser or desktop client, was showing up in Nextcloud's log as 10.244.0.0. A request goes through three hops to get there. The client talks to Traefik, Traefik talks to Nextcloud's Kubernetes Service, and the Service hands it off to whichever pod is backing it.

A request straight to Nextcloud's pod IP, skipping its Service entirely, came through with the real address intact:

$ wget -qO- --header="Host: cloud.khider.fr" http://<nextcloud-pod-ip>/status.php # Traefik's pod straight to Nextcloud's pod IP, no Service in between nextcloud access log: 10.244.3.137 - - "GET /status.php" 200 # Traefik's real pod IP, correct

So did a request straight to Nextcloud's own Service address instead of its pod IP:

$ wget -qO- --header="Host: cloud.khider.fr" http://nextcloud.nextcloud.svc.cluster.local:8080/status.php # through Nextcloud's Service, not its pod IP nextcloud access log: 10.244.3.137 - - "GET /status.php" 200 # still correct

That ruled out Nextcloud's own Service. Both tests used the same network path a real request takes, and both came through clean. They were manual requests run from a shell inside the Traefik pod, so they didn't go through Traefik's reverse-proxy code. The difference had to be in what Traefik does when it proxies a request.

A packet capture of a real Traefik-proxied request showed what Traefik was sending to Nextcloud. There was a Host header and nothing identifying the client, no X-Forwarded-For and no X-Real-Ip.

Host: cloud.khider.fr Host: cloud.khider.fr Host: cloud.khider.fr Host: cloud.khider.fr

Traefik was never sending the client's address to Nextcloud.

Resolution

  1. Configured forwardedHeaders.trustedIPs on Traefik's web and websecure entrypoints so it actually forwards a client-IP header to backends.
  2. Set externalTrafficPolicy: Local on the Traefik Service so it stops masquerading incoming traffic and Traefik gets handed the real client address to forward in the first place.

Each step was applied directly to the running cluster and checked against real traffic in the access log before being committed to the GitOps repo.

What went well

  • Ruling out both pod-to-pod paths narrowed it down to Traefik's proxy behavior, and a packet capture confirmed it before any fix was tried.

What went wrong

  • Traefik was deployed without checking what client IP its backends would see. Nothing tested it, so the gap sat there for two months until an app depended on it.

Follow-ups

  • Configure forwardedHeaders.trustedIPs on Traefik.
  • Set externalTrafficPolicy: Local on the Traefik Service.
