Postmortems

externalTrafficPolicy: Cluster rewrote every source IP

2026-09-09 Resolved SEV2 kubernetes traefik networking

I moved Nextcloud off a plain Docker instance and onto the Kubernetes cluster. That same night, its pod failed its readiness probe and dropped out of the Service for about twenty minutes, and Nextcloud started warning that a single address, 10.244.0.0, was being brute-force throttled. Both came from defaults in Kubernetes and Traefik that had been replacing every source IP since Traefik was first set up, two months before Nextcloud was deployed here. No data loss.

Impact

  • Down: the Nextcloud pod was not ready for about twenty minutes on migration night. Single replica, so the app was unreachable through Traefik for that whole window.
  • Degraded: brute-force protection bucketed every client, legitimate or not, under one shared identity, so unrelated traffic could throttle any single user.

Timeline

  • 21:31: Nextcloud's manifests land in the GitOps repo, the migration off the old Docker instance begins.
  • ~22:21, about an hour in: the pod goes not ready and stays that way. KubePodNotReady fires at 22:38, once it crosses the standard 15-minute threshold. It comes back around 22:42, after roughly twenty minutes down.
  • Later that same night: the Nextcloud admin overview starts showing the brute-force banner naming 10.244.0.0. That's what started this investigation.

Trigger

Moving Nextcloud onto the cluster. It was the first app behind Traefik that makes decisions based on the client's IP, through its brute-force protection.

Root cause

10.244.0.0 is the Flannel address of the node that received the traffic. Requests reach Nextcloud through Cloudflare, then Traefik. Cloudflare adds the visitor's IP to X-Forwarded-For, and Nextcloud's Apache reads the client address from the X-Real-IP header set by Traefik, which it trusts as a proxy because it sits in 10.0.0.0/8. The visitor's IP was lost at two points on the way.

  1. Traefik never saw the real peer. Its Service, the LoadBalancer that exposes it to the outside, had the default externalTrafficPolicy: Cluster. That setting lets any node accept incoming traffic and forward it to the Traefik pod, and kube-proxy rewrites the source address to the node's own address so the reply comes back the same way. Every connection reached Traefik from 10.244.0.0 instead of from a Cloudflare address.
  2. Traefik discarded Cloudflare's headers. Traefik only keeps an incoming X-Forwarded-For when the peer is listed in forwardedHeaders.trustedIPs. Nothing was listed, so it dropped the header Cloudflare had set and wrote its own X-Forwarded-For and X-Real-Ip from the peer address, 10.244.0.0. Nextcloud read that header and recorded every visitor under the same address.

Both of those had been true since Traefik was first deployed, two months before Nextcloud existed on this cluster.

Contributing factors

  • Throttling hit every request. Nextcloud slows down responses when it thinks it's under a brute-force attack. Every request looked like the same attacker, so the slowdown hit almost everything.
  • Few Apache workers, one replica. With most workers stuck on slow responses, there weren't enough left to answer the readiness probe in time. Kubelet marked the pod not ready, and with a single replica the app was unreachable.
  • Nothing else needed the client IP. No other app behind Traefik acts on the source address, so the gap went unnoticed for two months.

Isolation

Every real request, browser or desktop client, was showing up in Nextcloud's log as 10.244.0.0. A request goes through three hops to get there. The client talks to Traefik, Traefik talks to Nextcloud's Kubernetes Service, and the Service hands it off to whichever pod is backing it.

A request straight to Nextcloud's pod IP, skipping its Service entirely, came through with the real address intact:

$ wget -qO- --header="Host: cloud.khider.fr" http://<nextcloud-pod-ip>/status.php # Traefik's pod straight to Nextcloud's pod IP, no Service in between nextcloud access log: 10.244.3.137 - - "GET /status.php" 200 # Traefik's real pod IP, correct

So did a request straight to Nextcloud's own Service address instead of its pod IP:

$ wget -qO- --header="Host: cloud.khider.fr" http://nextcloud.nextcloud.svc.cluster.local:8080/status.php # through Nextcloud's Service, not its pod IP nextcloud access log: 10.244.3.137 - - "GET /status.php" 200 # still correct

That ruled out Nextcloud's own Service. Both tests used the same network path a real request takes, and both came through clean. They were manual requests run from a shell inside the Traefik pod, so they carried no forwarding headers, and Nextcloud logged the address that connected to it: Traefik's pod IP.

Real requests also arrive from Traefik's pod IP, yet they were logged as 10.244.0.0. Apache only replaces the connecting address when a trusted proxy sends X-Real-IP, so that address had to be coming from the header Traefik set. Traefik fills that header from the peer it sees, which pointed the investigation at what was happening in front of Traefik rather than behind it.

Resolution

  1. Set externalTrafficPolicy: Local on the Traefik Service so kube-proxy stops rewriting the source address and Traefik sees the real peer.
  2. Listed Cloudflare's published ranges and the LAN in forwardedHeaders.trustedIPs on the web and websecure entrypoints, so Traefik keeps the X-Forwarded-For header Cloudflare sets instead of replacing it.
  3. Pointed Nextcloud's Apache RemoteIPHeader at Cf-Connecting-Ip. With the first two fixes, Traefik's X-Real-Ip still held the Cloudflare edge address, while Cloudflare always puts the visitor's IP in Cf-Connecting-Ip.

Each step was applied directly to the running cluster and checked against real traffic in the access log before being committed to the GitOps repo.

What went well

  • Ruling out both pod-to-pod paths showed the address was coming from a header, which narrowed the search to the path in front of Traefik before any fix was tried.

What went wrong

  • Traefik was deployed without checking what client IP its backends would see. Nothing tested it, so the gap sat there for two months until an app depended on it.

Follow-ups

  • Set externalTrafficPolicy: Local on the Traefik Service.
  • Configure forwardedHeaders.trustedIPs on Traefik.
  • Read the client IP from Cf-Connecting-Ip in Nextcloud's Apache.
